🔬 Anatomy of a subagent

A subagent isn’t magic — it’s a Markdown file. Two zones, four key fields, one place on disk. Understanding the structure is what separates those who use it from those who creates.

6

Every time the conductor invokes a subagent, it is reading a file .md. This file has two required zones: o frontmatter (among the three traits ---) e o body (everything else comes later). The first zone configures the agent — defines its name, trigger, tools, and model. The second zone is the brain — defines who it is and what it does. Together, these two parts make up the complete subagent.

↑ The subagent equation: frontmatter (config) + body (brain) = complete agent.

Detailed content

1

📄 The .md file is the subagent

If you’ve already worked with skills in Claude Code, you've already seen the structure: a Markdown file with frontmatter at the top. A subagent is exactly that — a .md with a configuration frontmatter and an instruction body. It isn’t a binary, compiled code, or a plugin. It’s a text file that any editor can open.

🔑 Why this matters

When the file is plain text, you get three things for free:

  • •Readability — you read, understand, and edit it without a special tool.
  • •Version control — goes into Git with the project. Diff works.
  • •Portability — copy the folder .claude/agents/ to another project, and the agent goes with it.

📋 Skill (.claude/skills/)

Invoked with /skill-name · same model and tools as the chat · same context window.

🤖 Subagent (.claude/agents/)

Triggered by the description · separate window · distinct model and tools · returns only the report.

What it is:

A Markdown file with frontmatter + body. The analogy with skill.md is intentional — same structure, different purpose.

Why learn:

Demystify the subagent. There’s nothing hidden: everything the orchestrator knows about the agent is in this file.

Key concepts:

.md file · YAML frontmatter · Markdown body · versionable in git · portable across projects.

2

⚙️ Frontmatter (config) × body (brain)

The two zones have completely different responsibilities. The frontmatter is read by Claude Code to decide if it triggers the agent and how it will run. The body is the prompt sent to the model when it is invoked—it is literally that agent's "system." Confusing the two zones is the most common mistake when creating your first subagent.

.claude/agents/code-reviewer.md Markdown
⚙️ FRONTMATTER — configuration
---
name: code-reviewer
description: Reviews the current diff for bugs and
security failures. Use after any code change.
tools: Read, Grep, Glob
model: claude-sonnet-4-5
---
🧠 BODY — brain (prompt)
You are a senior code reviewer.
When invoked:
1. Run git diff to see what changed.
2. Read the changed files and understand the intent.
3. Review for correctness, security and missing tests.
Flag: bugs, security holes, and missing tests.
Be concise. Do not rewrite the code — only report.
↑ Illustrative recreation — the two sections of a subagent's .md file

⚙️ Frontmatter — what it does

  • ✓Defines the agent identifier (name)
  • ✓Describes when the orchestrator should use it (description)
  • ✓List the allowed tools (tools)
  • ✓Choose the model that will run (model)

🧠 Body — what it does

  • ✓Defines the agent's role (“You are a...”)
  • ✓Describes the execution steps
  • ✓Specify the output format
  • ✓List what the agent must NOT do
What it is: the division into two responsibilities: runtime configuration (frontmatter) and model prompt (body).
Why learn: without this distinction, you put instructions in the wrong place—you try to configure tools in the body or describe the role in the frontmatter.
Key concepts: YAML frontmatter between --- · free-form Markdown body · read at different times · non-interchangeable purposes.
3

🔑 The 4 key frontmatter fields

The frontmatter supports many fields, but four are the ones you’ll write in every subagent. The others — color, memory, disallowed-tools — they’re optional and covered in Track 2. For now, master these four.

1

name — identifier

Lowercase + hyphens, no spaces. Appears in logs and FleetView. Use descriptive names: code-reviewer > cr.

2

description — trigger

The conductor reads this field to decide when trigger the agent. Vague description = agent never triggered. Track 2 is entirely dedicated to writing good descriptions.

3

tools — permissions

Least privilege principle: reader agent → Read, Grep, Glob. Editor agent → add Edit, Write. Don't omit it — without declaring it, it inherits everything from the maestro.

4

model — who executes

Mechanical → haiku. Analysis → sonnet. Strategic reasoning → opus. Making an intentional choice here saves cost and time. Track 3 goes deeper.

💡 All available fields

In addition to the four above, the frontmatter accepts: color (color in FleetView), memory (project/user/local/none), disallowed-tools (explicit blocking) and advanced MCP fields. The official documentation lists them all — link in topic 6 of this module.

What it is: the four fields every subagent needs: name, description, tools, model.
Why learn: without all four, the agent isn’t triggered, uses too many tools, or runs on the wrong model.
Key concepts: name (id) · description (trigger) · tools (least privilege) · model (cost × quality).
4

🧠 The body: the brain’s four sections

The body is free-form Markdown — you can write whatever you want. But a well-formed body almost always has four parts. Think of them as sections in a briefing for a new employee: who you are, what to do, what to deliver e what never to do.

👤

Role (Role)

The first line of the body. Defines the agent’s identity.

You are a senior code reviewer
focused on security.
📋

Steps (Steps)

What to do when activated, step by step.

When invoked:
1. Run git diff.
2. Read changed files.
3. Look for bugs.
📤

Output (Output)

Format and content of what goes back to the orchestrator.

Report: a bullet list of
issues. Include file path
and line number.
🚫

Don't do (Limits)

Explicit boundaries — what the agent doesn't do.

From not rewrite code.
From not open new files
beyond the diff.

✓ Well-formed body

  • ✓Starts with "You are a..." — clear role
  • ✓Unambiguous, numbered steps
  • ✓Explicit output instruction (bullet, JSON, prose)
  • ✓At least one “Do not...” to limit scope

✗ Weak body

  • ✗No role—the model improvises its identity
  • ✗Vague steps: "analyze the code"
  • ✗No output instruction—the conductor doesn’t know what to expect
  • ✗No limits—the agent edits when it should only read
What it is: the body as a four-section briefing: role, steps, output, and limits.
Why learn: an incomplete body produces unpredictable agents — ones that do more (or less) than you expected.
Key concepts: role · steps · output format · limits · freeform Markdown.
5

📁 Where it lives: .claude/agents — the bridge to Track 2

Claude Code looks for subagents in .claude/agents/ in the project root. It’s a hidden folder, just like .claude/skills/ that you already know. Any .md Saved there, it’s automatically loaded as an available subagent— no restart, no registration command.

folder structure project 
seu-projeto/
├── .claude/
│   ├── agents/               # subagentes do projeto
│   │   ├── code-reviewer.md   # ← aqui!
│   │   ├── test-writer.md
│   │   └── doc-writer.md
│   ├── skills/               # skills (diferente!)
│   └── CLAUDE.md             # instruções do projeto
└── src/
    └── …

🗂️ Project — .claude/agents/

Only in this project · goes in git · shared with the team.

🌐 Global — ~/.claude/agents/

All projects · user’s home · personal agents.

🔭 Bridge to Track 2: In Track 2, you creates these files — complete frontmatter, actual body, and the command /agents to manage the catalog.

What it is: the .claude/agents/ folder as the mounting point for a project’s subagents.
Why learn: Knowing where to save is the first step to creating one. Without the right path, the agent won’t appear.
Key concepts: .claude/agents/ · project vs. global scope · automatic loading · versionable.
6

📚 Official documentation — all fields

The frontmatter supports more fields beyond the four essentials. The reference below covers the most commonly used ones.

📖 Frontmatter fields — quick reference

Field Required? What it’s for
name ✓ yes Unique identifier—lowercase and hyphenated
description ✓ yes Trigger — when the orchestrator invokes this agent
tools recommended Allowed tools (comma-separated list)
model recommended Claude model that executes (haiku / sonnet / opus)
color optional Badge color in FleetView
memory optional Memory access: project / user / local / none
disallowed-tools optional Explicitly blocks specific tools

Complete documentation: use /help agents in Claude Code (offline) or docs.anthropic.com/claude/code/agents. Advanced fields such as memory e disallowed-tools unlock extra behaviors covered in Track 3+.

What it is: reference for all fields — required and optional.
Why learn: Knowing where to find advanced fields saves trial and error when creating more sophisticated agents.
Key concepts: required × optional fields · /help agents · docs.anthropic.com/claude/code/agents.

Fully annotated .md example

Read this doc-writer.md with attention to the notes in comments. Each line is labeled with the section it belongs to and the reason it’s there.

.claude/agents/doc-writer.md annotated example 
--- ← delimitador de abertura do frontmatter

name: doc-writer
  ↑ identificador — minúsculas, hífens, sem acento

description: Escreve documentaçêo técnica e READMEs
  a partir de código existente. Use quando o usuário
  pedir para documentar um módulo, funçêo ou projeto.
  ↑ gatilho — 3 frases: o que faz, quando usar, sinal

tools: Read, Glob, Write
  ↑ menor privilégio — lê código, escreve .md, sem Bash

model: claude-sonnet-4-5
  ↑ sonnet: boa escrita, custo razoável. Haiku bastaria?
     Nêo — qualidade de prosa importa aqui.

--- ← delimitador de fechamento do frontmatter

# corpo (tudo aqui é o prompt enviado ao modelo)

You are a technical documentation writer.
  ↑ papel — identidade do agente (primeira coisa!)

When invoked:
1. Read the files listed in the task.
2. Identify the public interface (exports, classes, functions).
3. Write a clear README.md at the module root.
  ↑ passos — numerados, açêo concreta em cada um

Output: a single README.md file with:
  - One-sentence summary
  - Installation (if applicable)
  - Usage examples in code blocks
  - API reference table
  ↑ saída — formato explícito; o maestro sabe o que esperar

Do not invent behavior that isn't in the source code.
Do not modify source files — only create/update .md files.
  ↑ limites — dois "do not" que previnem alucinaçêo e dano

Exercise — Label the parts

Below is a file .md of a subagent with 8 numbered lines. For each line, identify: (a) which zone it is in (frontmatter or body), (b) which field or body section it represents.

L1---
L2name: test-writer
L3description: Writes unit tests for Python functions.
L4tools: Read, Write, Bash
L5model: claude-haiku-4-5
L6---
L7You are a Python test engineer.
L8When invoked, read the target file and write pytest tests.

✅ Criteria — you got it right if, for each line, you said:

  • →Area: frontmatter (L1–L6) or body (L7–L8).
  • →Field/section: delimiter, name, description, tools, model, role, or steps.
  • →Impact: what breaks if this line disappears.

Bonus: which tool in L4 is the riskiest, and why Bash requires care.

Answer key

L1,L6 → delimiters · without them, the YAML won't parse
L2 → frontmatter · name · without it, the agent loses its ID
L3 → frontmatter · description (activation trigger)
L4 → frontmatter · tools · Bash = unrestricted execution = higher risk
L5 → frontmatter · model · haiku = fast and cheap
L7 → body · role · model identity (comes first)
L8 → body · steps · execution instructions
