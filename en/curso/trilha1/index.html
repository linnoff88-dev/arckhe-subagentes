1.1 ~30 min

🎯 What a subagent is

A specialist you delegate to. The chat is the maestro; the subagent works in its own context window and returns a clean report.

What it is:

Your main chat is the conductor: it understands the request and decides what to delegate. The subagent is the specialist musician who handles one part.

Why learn:

Without this separation of roles, you try to do everything in a single conversation and lose control of what’s happening.

Key concepts:

Maestro = orchestrates and decides; subagent = performs a task and reports back.

What it is:

The subagent receives the task, opens its own context window, works, and returns only the result to the conductor.

Why learn:

This is the cycle that keeps your conversation lean — the grunt work stays in the subagent’s window.

Key concepts:

Dedicated window = isolation; report = only the essentials come back.

What it is:

Five different subagents can run in parallel, each with its own role, returning five summaries to the orchestrator.

Why learn:

Visualizing the fleet helps you understand the benefit: multiple workstreams at once, without mixing contexts.

Key concepts:

Parallelism = N independent windows; each persona = a specialist.

What it is:

The subagent doesn’t talk with you turn by turn. It gets a task, carries it out, and disappears—it’s not a second chat.

Why learn:

Expecting dialogue from the subagent is the most common mental error. Knowing what it is NOT avoids frustration.

Key concepts:

No back-and-forth; no memory of your conversation; one task.

What it is:

Each subagent speaks only to the conductor that called it. Subagents do not talk to each other.

Why learn:

Defines what can and cannot be orchestrated—and why coordination always belongs to the conductor.

Key concepts:

Star topology; the conductor is the only point of convergence.

What it is:

Claude Code comes with ready-to-use subagents (such as general-purpose). You can invoke one without creating anything.

Why learn:

Experimenting before theorizing makes the concept stick: you see the report come back clean in practice.

Key concepts:

Built-in = ready to use; delegate by asking “open a subagent to…”

🧹 The real reason: clean context

The #1 reason isn’t speed — it’s protecting the context window. Everything you read stays for the entire session; delegating keeps it clear.

What it is:

The context window is the session’s working memory. The status line shows how many tokens and what percentage you’ve used.

Why learn:

Whoever understands the window understands why delegation matters. It’s a finite resource you spend with every file you read.

Key concepts:

Context = limited resource; %/tokens = your budget.

What it is:

Everything you read in the main conversation — logs, files, large outputs — stays there taking up space until the session ends.

Why learn:

Polluted context degrades subsequent responses. Recognizing the pollution is the first step to avoiding it.

Key concepts:

Reading = ongoing cost; accumulated noise makes it harder to focus.

What it is:

Read 300 pages in the main conversation versus having a subagent read them and bring you only the 3 facts that matter.

Why learn:

It’s the course’s central decision. Internalizing the tradeoff changes how you work day to day.

Key concepts:

You = dirty context; subagent = preserved context.

What it is:

The subagent does the heavy lifting in its own window and returns a distilled summary—not the raw pile.

Why learn:

It’s what goes into your conversation. A good summary is the subagent’s output; you only see the gold.

Key concepts:

Distillation; the report is the interface between the two windows.

What it is:

Many people think subagents are about being faster. The main benefit is preserving context.

Why learn:

Targeting the right reason helps you use subagents in the right situations, not just “to go faster.”

Key concepts:

Context > speed; speed is a bonus, not the goal.

What it is:

A product research task involving huge documentation: the subagent reads it all and returns the 3 decisive points.

Why learn:

A concrete number makes the idea stick better than theory: hundreds of pages would cost half your context window.

Key concepts:

Compression ratio; the summary fits where the raw source wouldn’t.

1.3 ~35 min

⚖️ Agent × Subagent × Skill

The course's central comparison. Private vs. shared context, parallelism, its own model, and who calls whom.

What it is:

Agent = the main assistant; subagent = a specialist delegated to its own window; skill = an instruction/capability loaded into the current context.

Why learn:

Confusing the three leads you to use the wrong tool. One clear sentence for each unlocks everything.

Key concepts:

Three primitives, three roles; they're not synonyms.

What it is:

The subagent has its own isolated window; the skill runs inside the current agent’s shared context.

Why learn:

It’s the axis that makes the biggest difference: a skill dirties your context; a subagent protects it.

Key concepts:

Isolation (subagent) vs. in-place (skill).

What it is:

You can run multiple subagents in parallel; a skill runs within the agent’s sequential workflow.

Why learn:

When you need N fronts at the same time, only a subagent can deliver that.

Key concepts:

Parallel = subagent; inline = skill.

What it is:

A subagent can run on a different model than the orchestrator; a skill uses the model of the agent that loaded it.

Why learn:

It’s the foundation of savings: a cheap Haiku subagent while the lead stays on Opus.

Key concepts:

Model per agent; skill inherits the current model.

What it is:

Skills and agents call each other, but an agent does not invoke another agent — coordination always goes back to the conductor.

Why learn:

Defines the limits of orchestration. Trying to make an agent call another agent breaks the model.

Key concepts:

skill ↔ agent OK; agent → agent NO.

What it is:

A living table that cross-references context, parallelism, model, and invocation to point to the right primitive for each scenario.

Why learn:

It’s the deliverable you’ll refer to forever. Memorize the axes, not the cells.

Key concepts:

Decisions by axis; the table is the backbone of Track 1.

🔀 Built-in × Custom

The ready-made subagents (Explore, Plan, general-purpose) versus the ones you create. And the progressive disclosure trick.

What it is:

Claude Code comes with built-in subagents: Explore (search), Plan (architecture), general-purpose (all-purpose), and Claude itself.

Why learn:

Before creating anything, you already have powerful tools. Knowing which ones exist helps you avoid reinventing the wheel.

Key concepts:

Built-in = ready; covers search, planning, and general tasks.

What it is:

Giving the general-purpose agent a persona in a prompt doesn't create a custom subagent—it's just a temporary instruction.

Why learn:

This is a common mix-up. A true custom is a persistent, reusable file that runs on its own.

Key concepts:

Ad hoc persona ≠ saved agent; custom = file.

What it is:

A custom subagent is a Markdown file with frontmatter + body. It lives on disk and is always available.

Why learn:

It’s the bridge to Track 2. Understanding that “it’s just a .md” demystifies creating one.

Key concepts:

.md = subagent; frontmatter (config) + body (brain).

What it is:

Claude reads only the name and description of each agent until deciding to use one. The full body is loaded only when the agent is called.

Why learn:

Explains why the description is so important and why having many agents doesn't weigh down the context.

Key concepts:

Progressive disclosure; load the details only when needed.

What it is:

Since only name+description stay loaded, you can have dozens of agents without bloating the context.

Why learn:

Takes the fear out of “having too many agents.” The catalog is lightweight by design.

Key concepts:

Catalog cost ≈ metadata only; body on demand.

What it is:

The command /agents lists the available subagents (built-in and custom) and opens the creation assistant.

Why learn:

It’s the practical entry point. Before you create one, see what’s already there with a command.

Key concepts:

/agents = list + create; starting point for T2.

🤔 The question that decides

"Will this dump a bunch of stuff I’ll never reread?" Signs to use it, signs to avoid it, and the 10+ files rule.

What it is:

One question covers most cases: “Will this generate a pile I’ll never read again?” If so, delegate.

Why learn:

It’s the heuristic that saves you from memorizing lists. One phrase in your pocket is worth ten rules.

Key concepts:

Future reuse of the output = criterion; “reading junk” → subagent.

What it is:

Many files, a wall of output, a repeated task, independent jobs in parallel, or the need for an impartial reviewer.

Why learn:

Recognizing the quick green light helps you delegate at the right time, without hesitation.

Key concepts:

Volume, noise, repetition, parallelism, impartiality.

What it is:

Quick edits, dependent steps, agents that would need to talk to each other, when you need the full conversation or need to ask you a question.

Why learn:

Forcing a subagent where it doesn't fit creates rework. The red flag saves time.

Key concepts:

Speed, dependency, dialogue, personal context.

What it is:

Rule of thumb: 10+ files to scan or output you’ll never reread = subagent.

Why learn:

A number makes the decision objective when intuition falters.

Key concepts:

10-file threshold; output wall = trigger.

What it is:

When the job requires dozens or hundreds of subagents, you move to a dynamic workflow that orchestrates the fleet.

Why learn:

Marks the boundary between “one subagent” and “an operation at scale” — a topic explored in depth in Learning Path 3.

Key concepts:

Scale changes the tool; watch the cost.

What it is:

For something quick, doing it directly in chat is better. A subagent has startup costs—it isn’t worth using for everything.

Why learn:

Balance: the right tool for each task size, without dogma.

Key concepts:

Startup overhead; small tasks stay in the chat.

🧬 Anatomy of a subagent

Inside the .md file: frontmatter (the config) + body (the brain). Overview now, covered in depth in Track 2.

What it is:

There's nothing magical about it: the subagent is literally a Markdown file, with the same structure as a skill.md.

Why learn:

Demystify it once and for all. If you can edit text, you can create a subagent.

Key concepts:

File = agent; plain text, versionable.

What it is:

The top among --- is the frontmatter (YAML configuration); the rest is the body, the brain with the instructions.

Why learn:

Viewing both zones gives you the mental map for all of Track 2. Each has a distinct role.

Key concepts:

Frontmatter = how the agent is selected; body = how it acts.

What it is:

The essential frontmatter fields: name, description, tools e model.

Why learn:

With these four, you can already create a functional subagent. The rest is refinement.

Key concepts:

name (id), description (trigger), tools (permission), model (cost).

What it is:

A good body defines the role (“you are a…”), the numbered steps, the output format, and what NOT to do.

Why learn:

This structure is what separates a reliable agent from a generic one. It's the skeleton of Track 2.

Key concepts:

Role → steps → output → constraints.

What it is:

The file is in .claude/agents/ (in the project) or ~/.claude/agents/ (global) — topic of Track 2.

Why learn:

Knowing where it lives is what connects “create the .md” with “Claude finding and using it.”

Key concepts:

Folder determines scope; project vs. global.

What it is:

Beyond the 4 key fields, there are advanced fields (color, memory, disallowed-tools, MCP) documented officially.

Why learn:

You don’t need to memorize everything: you need to know that the complete reference exists and where to find it.

Key concepts:

4 fields to get started; official docs for the rest.
