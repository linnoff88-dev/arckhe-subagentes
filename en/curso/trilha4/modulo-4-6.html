🗄️ Your library of specialists

Agents are files. Files can be organized. Organization becomes power.

What it is

A library of specialists is a set of files .md with subagent definitions that you maintain and evolve. Each file is an “employee” with a clearly defined name, scope, tools, and restrictions. The library lives in two places: ~/.claude/agents/ (available in all projects) and .claude/agents/ within each project (repository-specific).

Why build your library

  • ▸Avoids rewriting the same system prompt every time—call the agent by name
  • ▸Well-defined agents make fewer scope errors — they know what they should not do
  • ▸Improves over time: fix a bad agent once and every project benefits
  • ▸Teams can share the library via git — an emerging organizational standard

Key concepts

Global (~/.claude/)
Available in any project. Ideal for universal specialists (security, docs, test).
Local (.claude/ in the project)
Domain specialists: a db-expert for your stack, a reviewer for your style guide.
Version-controlled (git)
Commit .claude/agents/ along with the code. An agent change = a PR like any other.

📦 Starter pack — 5 agents to get started today

security-auditor · test-runner · doc-writer · db-expert · plan-roaster

What it is

A set of five agents covering the most common use cases in software development. They’re generic enough for any stack, but specific enough to be useful without customization. Copy them, adjust the details for your project (database names, frameworks, testing conventions), and you have a functional suite in minutes.

Why these five

🔒
security-auditor
Vulnerabilities, exposed secrets, SQL injection, XSS—reads code, never executes it.
🧪
test-runner
Runs tests, interprets failures, and suggests fixes without touching production code.
📝
doc-writer
JSDoc, docstrings, README, changelog — writes, never refactors the code.
🗄️
db-expert
Explains queries, suggests indexes, reviews migrations — never executes DDL/DML.
🔥
plan-roaster
Critiques implementation plans, points out risks, plays devil’s advocate — without modifying code.

Key concepts

✓ Starter package principles
  • ✓Minimal tools (only what's needed)
  • ✓Explicit restrictions (“never execute X”)
  • ✓Well-defined scope per agent
  • ✓Output format specified
✗ Avoid in this first package
  • ✗Agents that do everything (no focus)
  • ✗Writing permissions without a reason
  • ✗System prompts over 200 lines
  • ✗Circular dependencies between agents

📐 Ready-made templates for your suite

Frontmatter + body in minutes, not hours.

What it is

An agent template has three parts: the YAML frontmatter (metadata that Claude Code reads), the system prompt (how the agent should behave) and the usage examples (optional but very useful). A good template is a shortcut for creating new agents — fill in the variable parts and you have a working agent in 5 minutes.

Why use templates

  • ▸Consistency: all agents in the suite have the same output structure
  • ▸Speed: new agent in 5 min without thinking about the structure
  • ▸Onboarding: a new contributor understands the convention without extra documentation

Key concepts — template anatomy

YAML frontmatter
name, description, tools, model (optional), disallowedTools
System Prompt (# Section)
Role, objective, required constraints, expected output format
Usage examples
When to use, when NOT to use, edge cases — saves a lot of time

✅ Production checklist

Before putting an agent into real-world use, go through this list.

What it is

A checklist is the last filter before an agent becomes part of your permanent library. It covers security (minimum tools, no unnecessary permissions), quality (clear system prompt, defined output format), and operations (who calls it, when, what happens if it fails).

Why use a checklist

1. Safety first
Review each tool: is it really necessary? Can the agent cause harm if misinstructed?
2. Scope clarity
Can someone who’s never seen the agent understand what it does in 30 seconds?
3. Output format
Is the output parseable? Does the orchestrator know what to expect?
4. Test with a real case
Run it on a concrete case before considering it ready. Failures reveal gaps in the system prompt.
5. Minimal documentation
Add when to use and when NOT to use to the frontmatter. It saves questions later.
⚠️
Common pitfall
Agents with Bash without restrictions, subprocesses can create loops or consume resources unexpectedly. Always test in an isolated environment first.

Key concepts — the concise checklist

☑Tools are the minimum necessary
☑disallowedTools listed if applicable
☑System prompt ≤ 150 lines
☑Output format specified
☑Tested with a real-world case
☑When NOT to use, as documented

🔀 Project × Global in practice

What goes to ~/.claude/ and what goes in .claude/?

What it is

Claude Code resolves agents in two scopes: global (~/.claude/agents/) and local (.claude/agents/ in the project). If an agent exists in both places with the same name, the local one overrides the global one — allowing you to "override" generic specialists with project-adapted versions without removing the global one.

Why this matters in practice

~/.claude/agents/ (Global)
  • • generic security-auditor
  • • universal doc-writer
  • • default plan-roaster
  • • Agents for constant personal use
.claude/agents/ (Project)
  • • project stack db-expert
  • • test-runner with the right framework
  • • style-reviewer for the team guide
  • • Domain-specific agents
💡
Practical tip: override hierarchy
Start with the generic agent in the global scope. When a project has specific needs, create a local version with the same name. Claude Code uses the local one automatically — no configuration needed.

Key concepts

Override by name
Local overrides global when the filename is the same.
Version control
Local agents go in git. Global agents stay on the developer’s machine.
Naming convention
Use kebab-case. The name=identity. Avoid generic names like “helper.”

📄 Real example — a package of 5 agents (.md)

Five files ready to copy to ~/.claude/agents/ or .claude/agents/:

# ~/.claude/agents/security-auditor.md
---
name: security-auditor
description: Audita código em busca de vulnerabilidades de segurança. Use para revisar PRs críticos, módulos de autenticaçêo, inputs de usuário. NêO use para refatoraçêo.
tools:
  - Read
  - Bash  # somente leitura — sem escrita de arquivo
disallowedTools:
  - Write
  - Edit
---

# Security Auditor

Você é um especialista em segurança de aplicações. Sua única funçêo é revisar código e apontar vulnerabilidades.

## O que você faz
- Identifica SQL injection, XSS, CSRF, secrets expostos, dependências com CVE
- Classifica cada achado: CRÍTICO / ALTO / MÉDIO / BAIXO
- Sugere correçêo específica para cada achado

## O que você NêO faz
- Nêo modifica arquivos
- Nêo sugere refatoraçêo fora do escopo de segurança
- Nêo executa código de produçêo

## Formato de saída
```markdown
## Relatório de Segurança — [arquivo/PR]
### Achados
| Severidade | Linha | Descriçêo | Correçêo sugerida |
```
# ~/.claude/agents/test-runner.md
---
name: test-runner
description: Roda suítes de teste, interpreta falhas e sugere correções. Ideal para CI debug e TDD. Use ANTES de mergear.
tools:
  - Bash
  - Read
disallowedTools:
  - Write
  - Edit
---

# Test Runner

Roda testes, lê a saída e explica cada falha em linguagem humana. Sugere correçêo mas nêo aplica.

## Regras
- Rode sempre com `--no-coverage` para velocidade na primeira passagem
- Agrupe falhas por módulo (nêo por arquivo)
- Priorize: build breaks > falhas de lógica > warnings
# ~/.claude/agents/doc-writer.md
---
name: doc-writer
description: Gera documentaçêo técnica (JSDoc, docstrings, README, CHANGELOG). Use após implementaçêo. NêO faz refatoraçêo.
tools:
  - Read
  - Write   # só para arquivos de documentaçêo (.md, comentários)
---

# Doc Writer

Especialista em documentaçêo técnica. Lê código e gera docs claros, concisos e atualizados.

## Convenções
- JSDoc para funções públicas
- Docstrings para funções com lógica nêo-óbvia
- README: instalaçêo, uso, exemplos mínimos
- CHANGELOG: formato Keep a Changelog
# .claude/agents/db-expert.md   (local — adapte ao projeto)
---
name: db-expert
description: Especialista em banco de dados do projeto. Revisa queries, migrations e índices. NêO executa DDL/DML.
tools:
  - Read
  - Bash    # apenas queries SELECT em banco de dev
disallowedTools:
  - Write
---

# DB Expert — [nome do projeto]

Stack: PostgreSQL 15, Prisma ORM, ambiente dev em localhost:5432.

## O que faço
- Analiso N+1, missing indexes, cartesian products
- Reviso migrations antes do deploy
- Explico planos de execuçêo (EXPLAIN ANALYZE)

## Formato de resposta
Para cada problema: impacto estimado + query corrigida + índice sugerido.
# ~/.claude/agents/plan-roaster.md
---
name: plan-roaster
description: Critiques implementation plans with constructive skepticism. Use before any complex task. Does NOT modify code.
tools:
  - Read
disallowedTools:
  - Write
  - Edit
  - Bash
---

# Plan Roaster

You are the technical devil's advocate. You read plans and point out what will go wrong.

## How you work
1. Read the complete plan
2. List implicit assumptions (the most dangerous ones)
3. Point out failure points: edge cases, external dependencies, difficult rollback
4. Suggest questions the author should answer before starting

## Tone
Direct and useful. Not pessimistic by nature — just realistic.

💬 Ready-to-use prompts

Prompt 1 — Generate an initial suite for the current project
Analyze this project and create 5 custom subagents for me in .claude/agents/. For each one: identify the most-needed role, define the minimum tools and explicit restrictions. Format: one code block per .md file, ready to copy. Start with the most impactful.
Prompt 2 — review an existing agent with a production checklist
Leia o arquivo .claude/agents/[nome].md e aplique o checklist de produçêo: ferramentas sêo mínimas? restrições explícitas? escopo claro em 30s? formato de saída definido? Aponte problemas e sugira versêo corrigida.
Prompt 3 — orchestrator dispatcher for the full suite
Usando os subagentes disponíveis (security-auditor, test-runner, doc-writer, db-expert, plan-roaster), monte um workflow para revisêo completa antes de PR: rode os agentes relevantes em paralelo, colete resultados e gere um relatório unificado com ações prioritárias. Comece pelo plano antes de executar.

Final Project

Design and create your own subagent suite

What to do

  1. Choose a real project you have or are developing.
  2. Identify the 3 recurring bottlenecks in your workflow (examples: "I review security manually," "I test by hand," "it takes me too long to document").
  3. For each bottleneck, design a subagent: name, tools, constraints, output format.
  4. Create the files .md in .claude/agents/ from the project.
  5. Test each agent on a real-world case and document what worked and what you adjusted.
  6. Write one paragraph: "My suite does X. It used to take me Y. Now it takes me Z."

✓ Completion criteria

  • ✓≥ 3 .md files created and working
  • ✓Each agent passed the production checklist
  • ✓Each agent tested on a real case (not simulated)
  • ✓An honest, well-written impact paragraph
  • ✓At least 1 agent committed to the repository

✗ The exercise doesn’t count if

  • ✗The agents were only imagined, not created
  • ✗None were tested with a real task
  • ✗The "project" is a hello world created just for the exercise
  • ✗The impact paragraph was generated by AI without an honest review
